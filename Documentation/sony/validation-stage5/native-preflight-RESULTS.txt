New production-code cases exercise legacy->opt-in and opt-in->legacy child
orders with registration-time voting enabled. Both reject with zero endpoint
lookup, allocation, claim, legacy/physical publication, activation or transport,
and one explicit OF node put. A legacy-only module still registers and sends
the requested constraint vote. Removing only the probe preflight (leaving
per-child opt-in rejection) is rejected by the new negative. All seven earlier
selector/load/offline/final-rdev/parent-retention/lock mutations also reject;
the last-consumer-vs-removal and blocked-write retirement cases still pass.

Retained-parent/lifetime review boundaries:
- Builtin supplied registrations intentionally remain inert after retirement;
  immutable desc.supply_name covers unresolved and concurrently resolving
  supplies, while preserved common tuple claims bound repeated reprobes.
  The registry also compares stable OF endpoint paths and retains its RPM/OF
  references, so a new transport generation cannot silently reset that guard.
- Parentless callback storage remains tied to final rdev device release.
- This is not a provider release/reset contract, a physical rail disable, or
  proof that regulator-core supply preambles perform no upstream operations.
- Pure legacy module RPMSG hotremove with surviving consumers is still outside
  Dora's builtin qualification: core unregister can free an upstream supply
  handle before a surviving child's next core supply preamble. Normal rmmod
  module pinning does not establish safety for that separate hotremove path.
  The opt-in preflight fixes partial mixed-bank publication, not this old core
  module-removal boundary.
- Failed native registration after upstream supply resolution remains the
  existing opaque regulator-core failure-cleanup boundary. The harness executes
  native production helpers but models these core APIs; it does not claim to
  repair that core failure path, nor to validate firmware or real removal.
